# Furniture Store Sales Forecasting (SQL + Python ML)

Forecasts monthly furniture sales from the Superstore dataset (2,121 order lines, Jan 2014 - Dec 2017).

## Pipeline
1. `01_create_db.py` - loads the CSV into a normalized SQLite DB (`sql/schema.sql`: customers, locations, products, orders, order_items) and creates SQL views (`sql/views.sql`).
2. `02_forecast.py` - reads `monthly_sales` via SQL, trains 4 models, evaluates on 2017, writes `model_metrics` and `predictions` tables back to the DB.
3. `app.py` - Streamlit dashboard (forecast, model comparison, SQL analytics).

## Run
(`sales.db` is generated by the scripts, so it is not committed to Git.)

```
pip install -r requirements.txt
python 01_create_db.py
python 02_forecast.py
streamlit run app.py
```

## Key design choices
- Time-based split: train 2014-2016, test 2017. A random split would leak future data.
- Monthly aggregation: daily data is too sparse (about 2,100 rows over 4 years).
- Features (no leakage): lag 1/2/3/12, 3-month rolling mean, month, quarter.
- Multi-step recursive forecasting: each prediction feeds the next lag, so test scores are honest.
- Baseline: seasonal naive (same month last year). Any model must beat it to be worth using.
- SQL: JOINs, GROUP BY, views, `LAG()`, `AVG() OVER`, `SUM() OVER (PARTITION BY ...)`, `RANK() OVER`.

## Results (2017 hold-out)
| Model | MAE | RMSE | MAPE % |
|---|---|---|---|
| Seasonal Naive | 3747 | 4473 | 24.1 |
| Gradient Boosting | 3588 | 4713 | 25.6 |
| Random Forest | 3840 | 4779 | 21.6 |
| SARIMA | 6032 | 7144 | 57.1 |

Honest takeaway: with only 36 training months, the models barely differ from the seasonal baseline. Gradient Boosting has the best MAE and is used for the 6-month forecast; SARIMA struggles because of the highly irregular series.

## Limitations / future work
- Only 4 years of data; add holiday flags, discount and order-count features.
- Add prediction intervals; try Prophet.
- Move to MySQL/PostgreSQL by swapping the SQLAlchemy connection (window functions are standard SQL).
